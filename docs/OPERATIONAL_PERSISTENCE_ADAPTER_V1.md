# Operational Persistence Adapter V1

## Purpose

This adapter is the first connection between the operational JSON pipeline and
the SQLite persistence foundation.

It reads:

```text
data/decision_intelligence.json
data/shipment_evidence_queue_v1.json
```

and writes through `OpportunityRepository` into:

```text
opportunities
shipment_evidence_tasks
status_history
source_runs
```

JSON remains the official operational report format. SQLite stores durable state
and history; it does not become a new decision engine.

## P4 position

```text
decision_intelligence.json
        ↓
operational landed cost
        ↓
operational transport input
        ↓
shipment evidence queue
        ↓
Operational Persistence Adapter V1
        ↓
SQLite through OpportunityRepository
        ↓
synchronize dashboard and alerts
```

If persistence fails, P4 returns a failure before synchronizing consumers. All
writes occur in one transaction, so a bad task cannot leave a partially saved
opportunity.

## Integrity checks

The adapter verifies:

- `decision_count` equals the actual decision list length.
- opportunity identities are unique.
- queue task counts match the task list.
- blocking task counts are accurate.
- the selected opportunity exists exactly once in decision intelligence.
- copied `final_decision` and `opportunity_score` match the official decision.
- every task belongs to the selected opportunity.
- task identities are unique.
- a zero selection contains no opportunity or tasks.

## Stored data

For a selected opportunity, the adapter stores:

- the complete official decision snapshot;
- its existing `final_decision` and `opportunity_score` without recalculation;
- market code `NO` unless an explicit matching value already exists;
- all shipment-evidence tasks in the current queue;
- initial and changed status history generated by the Repository;
- one source-run record describing the persistence operation.

For a zero selection, it stores only a valid `source_runs` record with
`zero_result=true`.

## Replay behavior

Replaying the same JSON snapshot:

- refreshes the opportunity and tasks;
- does not duplicate decision or task status-history entries when statuses did
  not change;
- records a separate source run when a new `run_id` is used.

V1 does **not** automatically resolve or delete an older task merely because it
is absent from a later queue. Automatic reconciliation needs an explicit policy
and is deferred to a later version.

## CLI

```bash
PYTHONPATH=src python scripts/persist_operational_state.py
```

Explicit inputs:

```bash
PYTHONPATH=src python scripts/persist_operational_state.py \
  --decisions data/decision_intelligence.json \
  --shipment-evidence data/shipment_evidence_queue_v1.json \
  --database-url sqlite:///data/opportunity_engine.db
```

The CLI applies Alembic migrations before opening the Repository transaction.

## P4 configuration

The P4 command accepts:

```text
--database-url
```

Default:

```text
sqlite:///data/opportunity_engine.db
```

Local SQLite files are ignored by Git. A GitHub-hosted runner has ephemeral
storage, so its SQLite file does not survive a later run unless a separate
durable storage strategy is introduced. This PR does not commit a binary
database file and does not add an external database service.

## Safety boundary

The adapter does not:

- recalculate `final_decision`;
- recalculate scores or rankings;
- change Top 5 or alerts;
- modify JSON reports;
- contact sellers or carriers;
- request transport quotes;
- resolve tasks automatically;
- buy, bid, approve, or reject opportunities;
- add PostgreSQL, Docker, an API, or an external network request.
