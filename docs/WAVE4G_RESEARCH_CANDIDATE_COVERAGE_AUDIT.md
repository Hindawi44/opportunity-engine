## Historical workflow contract

The workflow is manual-only and exposes three required inputs:

| Input | Default | Purpose |
|---|---:|---|
| `opportunity_limit` | `20` | Limits the fresh dataset generated by `run_daily_pipeline.py`. |
| `research_threshold` | `25` | Inclusive preliminary research eligibility threshold. |
| `selection_limit` | `3` | Maximum eligible candidates selected for later external research. |

The workflow sets `EXTERNAL_RESEARCH_MAX_OPPORTUNITIES=0`, generates a fresh real dataset, runs `scripts/run_research_candidate_audit.py`, writes `data/validation/v2.7.2.4.1-research-candidates.json`, prints the report when present, and uploads artifact `v2.7.2.4.1-research-candidate-audit` for 14 days.

Artifact paths are:

```text
data/validation/
data/todays_opportunities.json
data/investment_files/
```

The upload step uses `if-no-files-found: warn`.

## Implementation behavior

`PreliminaryResearchCandidateScorer`:

- accepts payload lists or dictionaries under `rows`, `opportunities`, `items`, `results`, or `data`;
- derives preliminary score components from `score_breakdown`;
- adds listing-completeness points;
- applies heavy-asset, warning, and risk penalties;
- clamps the score to `0..50`;
- sorts by descending candidate score and then ascending `opportunity_id`;
- treats the threshold as inclusive (`score >= threshold`);
- truncates selected eligible candidates to `selection_limit`;
- normalizes negative selection limits to zero;
- keeps preliminary eligibility separate from final investment score and its fixed threshold of `60`;
- performs no external-research execution.

The CLI reads one dataset file, parses JSON, builds the report, creates the parent output directory, writes sorted/indented UTF-8 JSON, prints the complete report, and returns exit code zero on success. Missing files, invalid JSON, invalid numeric arguments, and write failures are not caught and therefore fail through normal Python exceptions or argparse behavior.

## Why the decision is NOT_READY

The historical workflow is more than the scorer class. Its material contract includes a fresh live-data boundary, three manual inputs, a CLI and real filesystem boundary, a versioned validation report, exact artifact contents, retention policy, and GitHub Actions failure/warning behavior. Current tests prove important algorithmic behavior but not this complete operational contract.

A final preservation run would therefore be premature because failures could not yet be distinguished confidently between live-source drift, workflow wiring, CLI/file behavior, artifact packaging, or scorer behavior.

## Required work before reconsideration

At minimum, a later coverage task should add focused verification for:

1. threshold equality and below/above cases;
2. deterministic tie ordering;
3. zero, negative, and oversized selection limits;
4. malformed and missing score-breakdown data;
5. accepted payload container shapes and empty/invalid shapes;
6. CLI defaults and explicit argument propagation;
7. missing file, malformed JSON, and output-write failures;
8. exact serialized schema and output path;
9. stdout behavior;
10. workflow-level confirmation that external research remains disabled;
11. exact artifact name, inventory, retention, and missing-file warning semantics;
12. a deterministic fixture boundary separate from the live preservation run.
